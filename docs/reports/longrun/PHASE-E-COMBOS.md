## 1. 为什么还要扫一次

Phase C 的细窗只扫了“第一次输入”的 lead：BRO DIVE 0.18–0.25 s，BRO OLLIE 0.14–0.19 s。但这两个动作都是**两段输入**：

- BRO DIVE：兔子跳 → SHIFT → 乌龟按住 ↓；
- BRO OLLIE：乌龟跃 → SHIFT → 兔子蹬踏。

Phase C 的探针把第二段固定在“离地第一帧 / x≥start−70”，所以它只能证明“这个动作存在”，不能回答“玩家按完第一段后还有多久按第二段”。本阶段把第二段也变成扫描轴。

## 4. 读法

### 4.1 BRO DIVE：是“跳 + 立刻换人下潜”，不是两次独立计时

- 通过区是一条**斜带**：跳得越早（lead 越大），可以越晚按第二段；跳得越晚，第二段必须越早。
- 在 Z1，第二段的最佳窗口是 0.00–0.15 s；也就是说，**最自然的做法（跳完立刻 SHIFT+↓）是成立的**，玩家不需要等。真正的风险是“犹豫了一下才换人”——超过 0.15 s 就会龟撞。
- Z2/Z3 的窗口随速度增大到 0.20/0.25 s，因为前距更长、玩家有更多余量。
- 结论：BRO DIVE 的完整动作是**可执行的**，但 Z1 第一次教它时，第二段只有 0.15 s 的“犹豫预算”。这比 Phase C 的 0.18 s 起手窗口更紧。

### 4.2 BRO OLLIE：是“跃起后等 0.4 s 再蹬”，早按必失败

- 通过区的第二段**最早只能从 0.40 s 开始**；0.00–0.35 s 的格子全部失败（兔撞楣或落水）。原因是乌龟跃起前 0.4 s 壳还太低，兔子从壳上蹬出去也够不到墙楣顶。
- 最佳窗口：Z1 0.25 s（0.40–0.65）、Z2 0.35 s（0.40–0.75）、Z3 0.30 s（0.40–0.70）。
- 结论：BRO OLLIE 是“跃起 → 等 → 蹬”的节奏动作，**不能靠连按**。Z1 的 0.25 s 对第一次见的玩家偏紧，但它是可学的；Z2 的 0.35 s 说明这个动作本身有可扩展的余量。

### 4.3 与 Phase C 的关系

- Phase C 的“0.14–0.25 s”是**起手窗**；本阶段的“0.15–0.35 s”是**第二段窗**。两者不能相加，因为 lead 和 delay 是联合的。
- 两种连招都不是“纯动画假动作”：失败通道会随 lead/delay 改变，说明物理轨迹是独立的。
- 仍然没有验证：真人第一次见到这两个动作时，能否在 0.15/0.25 s 内完成第二段。**这是 NOT TESTED。**

## 5. 建议（交给 Phase D/H，不在本阶段改）

1. **不改结构**。两种连招都成立，且都有明确的失败面；先保留。
2. **Z1 的 log1 是唯一低于 0.25 s 的完整窗口**。如果 Phase H 要动，优先把 log1 的上下沿各放宽 6–8 px（或把 log1 的宽度从 32 降到 28），目标是把最佳延迟窗从 0.15 s 拉到 ≥0.20 s；不要改 Z2/Z3 的浮木。
3. **Z1 的 wall1 第二段 0.25 s**：可以接受，但第一次教学时建议把 wall1 的 lead 窗略微放宽（墙窗口下沿 −8 px 或墙宽 30→26），让“等 0.4 s”更容易落在窗口里；不要降低 `LEAP_TIME`。
4. 若后续加输入缓冲，只对 SHIFT 做 0.08–0.10 s 的预输入，不要对 ↑ 做自动蹬踏——后者会把“等 0.4 s”的节奏判断变成自动连招。
